# ADR 0015: Permissions and the audit chain

Status: accepted

## Context
Sign-in (ADR 0014) answers who is calling. Two questions were left open: what a signed-in user may do, and how the instance proves what happened. Every later feature (servers, runs, the vault, the terminal) needs both before it can exist: a route without a permission check is open to every user, and an action without an audit entry cannot be reviewed.

## Decision

### Permissions
- **A permission is a `resource:action` string from one closed catalogue** in `packages/contracts` (`servers:read`, `runs:execute`, `vault:reveal`, `audit:read`, ...). The server, the console and the OpenAPI document read the same list. A permission that implies another is listed with it: a role that can write a resource can also read it (a test checks this).
- **Roles are sets of permissions.** The five built-in roles (`owner`, `operator`, `observer`, `terminal`, `auditor`) are fixed in code, so a release changes them in one reviewed place. `owner` holds every permission of the catalogue, computed, so a new permission reaches the owner at once and every other role gets it only by a deliberate edit. The role `terminal` is the read-only set plus `terminal:use`; `auditor` reads everything, including users, roles and the audit log, and verifies the chain; `operator` runs and edits servers and the panel and sees the vault status, but cannot reveal a secret or open the terminal. Custom roles (the `Role` and `RolePermission` entities of the data model) wait for user management, because a role nobody can assign is not useful.
- **A route declares its permission in the registry** (`permission`), next to its `auth` level. A `PermissionGuard` runs after the authentication guard and answers 403 `forbidden` when the user's role lacks it. A test fails the build for a signed-in route that has no permission and is not on the short list of routes open to every signed-in user (`getMe`). The OpenAPI document carries the permission as `x-sw-permission`.
- **The role is read from the user row on every request.** A session holds no copy of the permissions, so changing a role or disabling a user takes effect on the next call.
- **The console only reads the permission list** (`permissions` in the session) to show or hide pages. It is a convenience: every route checks again on the server.

### The audit chain
- **An append-only table, `audit_events`.** Every row has a sequence number, the time, the actor (user id and the login name at that moment, kept as text so the record survives the removal of the user), the action, the outcome (`success`, `failure`, `denied`), the object, the client address, the request id, a few details, the hash of the previous row and its own hash.
- **The hash chain.** A row's hash is SHA-256 over the canonical JSON of its fields in a fixed order with a format version first and the previous hash last; the first row links to a fixed genesis value. Sequence numbers are assigned inside a short transaction under a PostgreSQL advisory lock, so they have no gaps and no two rows share a predecessor.
- **Immutable in the database as well.** The migration installs triggers that refuse `UPDATE`, `DELETE` and `TRUNCATE` on the table. This stops mistakes and an attacker who has only the application's access; it does not stop someone who owns the database.
- **Details are small and safe.** A record carries a flat object of short strings, integers and booleans, never a secret, never a code and never text typed by an unauthenticated caller: a failed sign-in with an unknown name stores no name (people paste passwords into that field). The details are stored as the exact canonical text that was hashed, not as `jsonb`, so reading them back cannot change the hash.
- **Failure policy.** A record that documents a change (an owner created, a sign-in completed, an authenticator enrolled) is written strictly: if the write fails the request fails, and the owner's creation and its record are one transaction. A record of something that was refused (a wrong password, a denied call, a sign-out) is best effort: a failing audit store must not turn a 401 into a 500 or lock people out of signing out; the failure is logged.
- **Bounded growth.** The log is never pruned, so what a caller can provoke is capped: sign-ins for unknown or disabled accounts at ten per address per quarter of an hour, refusals at twenty per user per ten minutes; sign-in attempts while an account is locked are not recorded one by one (the lock itself is). The server log still has every one.
- **Reading and verifying.** `GET /audit` lists newest first with a cursor and filters by action, outcome and actor; `POST /audit/verify-chain` walks the whole log, checks the numbering, the links and every hash, and answers with the first problem and the current head (sequence number and hash). Verifying is itself recorded. Reading the log requires `audit:read`, verifying `audit:verify`.
- **What is recorded now:** the first-run owner (`setup.owner.created`, `setup.owner.refused`), sign-in (`auth.login.failed`, `auth.second_step.failed`, `auth.login.succeeded`, `auth.totp.enrolled`, `auth.recovery_code.used`, `auth.account.locked`, `auth.logout`), refused access (`authz.denied`) and verification (`audit.chain.verified`). Later features add their own actions to the catalogue; actions are text in the database, so that needs no migration.

## Consequences
- The chain shows that rows were edited, removed or reordered by anyone who cannot recompute the whole chain. Someone who can write to the database can rewrite every row and fix every hash. Noting the head (`seq` and `hash`, shown by the console after a verification, and visible in every listing) somewhere outside the database turns that into a detectable event, and so will the signed checkpoints and the export planned with the rest of the audit tooling. This is stated here so the log is not trusted for more than it gives.
- All writes take one lock for a few milliseconds. At the rate of human and run events this is invisible; a high-volume source would need batching, which the format allows.
- Verification reads the whole table. It is meant for an owner or auditor to run now and then, not on every request; checkpoints would bound its cost.
- Export, retention policy and the audit view of other sources (runs, approvals, the vault, the terminal) come with those features. Permissions for features that do not exist yet are in the catalogue so the roles are stable; nothing enforces them until their routes exist.
- Removing a built-in role's permission or adding one to a role other than the owner is a visible change in `packages/contracts`, which is the intent.
