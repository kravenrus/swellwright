# ADR 0028: Running plugins in a restricted process

Status: accepted

## Context
ADR 0027 decided which plugins are approved, and that an approval holds only for the files that were approved. Nothing ran them. `13-plugins-and-opensource.md` (section 6) asks for plugins to run in a worker process with restrictions, to reach the network only through the core, to get no secret that is not theirs, to have limits on memory and call time, and to be disabled at once without restarting the core. It also says in-process isolation in Node is not a hard boundary and must never be relied on for untrusted code: container sidecars are for that, and they are a later step.

## Decision
- **One process per plugin, under the Node permission model.** The host (`PluginHostService`) starts a plugin's process on the first call or check, with `--permission`, read access to the plugin's own directory and to one file (the runner), no other `--allow-*` flag (so no writing, no network, no child processes, no workers, no native addons, no WASI, no inspector), `--disallow-code-generation-from-strings`, and a heap limit (`SW_PLUGIN_MEMORY_MIB`, 128 by default). The working directory is the plugin's, the environment holds nothing of the core's (only `SystemRoot` on Windows, which Node needs to start). If the runtime cannot apply the flags the start fails; there is no unrestricted fallback.
- **What was measured** (Node 26.13.1, Windows, with the real runner; the same tests run in CI on Linux): the plugin reads its own module; reading any other file, writing, running a program, starting a worker, a direct network connection (`fetch`, TCP, UDP, DNS lookups), `eval` and `new Function`, and `process.binding` are all refused; the environment holds no variable of the core; a method that allocates without end ends the process (exit 134 at the heap limit); a method that never returns is ended by the deadline.
- **What is not stopped, and why this is not a sandbox.** The permission model does not cover signals: a plugin process can send one to another process of the same user, the core included (`process.kill(process.ppid, 0)` succeeds; it was checked). A hostile plugin can therefore at least end the core. So the process is a defence for mistakes and for the common misuse (reading files, reaching internal addresses, spawning programs, leaking the environment), and not a boundary against code written to attack the server. `local` code stays the administrator's responsibility (ADR 0008, 0027), the console says so in plain words when enabling, and untrusted (`community`) plugins are for container sidecars, which this step does not build.
- **The only door out is the core.** The runner (one file that imports nothing of the application) loads each module the manifest names under its extension kind and answers calls over the IPC channel; its context offers `fetch` and nothing else. The core's gateway (`PluginNetwork`) lets a request through only if: the URL is `https` with no user or password; its `host:port` is exactly one of those the administrator approved (the stored approval, not the file as it is now); the method is an ordinary one; the body is at most 1 MiB; at most four requests of a plugin are in flight; the name resolves, and **every** address it resolves to is public (loopback, private, link-local, shared, reserved, multicast, documentation ranges and IPv4-mapped forms of those are refused). The connection is made to the address that was checked, with the name only for the certificate and the `Host` header, so a name that changes its answer between check and connection gains nothing. Redirects are not followed, the answer is text of at most 4 MiB, and the request ends after 15 seconds.
- **Verified before every start and every call.** The plugin must be enabled and have the digest that was approved (ADR 0027); a plugin that is not is switched off right there and no process starts. When a plugin is disabled or found changed its process is ended at once, nothing else restarts.
- **Limits that hold whatever the plugin says.** A call has a deadline (`SW_PLUGIN_CALL_TIMEOUT_SECONDS`, 10 by default) after which the process is killed and the call fails; at most 8 calls are in flight; an idle process is stopped after `SW_PLUGIN_IDLE_MINUTES` (10); a plugin that fails three times within a minute is left alone for the minute (the administrator's own check still goes through). A start that does not finish in ten seconds fails.
- **What a module looks like** (`@swellwright/plugin-api`, `definePlugin`): `export default { methods: { name(params, context) { ... } } }`, named in `provides[].entry`. Methods are found among the module's own properties only, so `constructor` or `toString` are not callable. Results travel as JSON.
- **Declarative plugins have no process.** A plugin that provides only drivers in data (`driver`) has nothing to run; a check says so. The interpreter of drivers is a later step.
- **The check.** `POST /plugins/{id}/check` (`plugins:manage`, step-up) starts the enabled plugin, loads its modules and reports what loaded and which methods each offers, or why it did not; a failure to load is an answer (200 with `runtime.state: failed`), not an error. Every check is recorded (`plugin.checked`, with the counts or the reason). `GET /plugins` shows the runtime of every plugin: state, when it started, how many calls, the last error, the modules and their methods.
- **Records.** `plugin.failed` (a call timed out or the process died) and `plugin.network.denied` (the host and the reason) are notes without an actor, at most five per plugin per ten minutes, so a plugin cannot fill the chain.
- **Not provided yet.** The manifest may ask for `secrets`, `panel` and `ssh` and the administrator approves them (ADR 0027), but no broker hands a secret, a panel call or an SSH command to a plugin yet: a plugin gets only `fetch`. Brokers come with the first plugin that needs one.

## Consequences
- An approved plugin can now run, with the files it was approved with, unable to read the server, reach its network or its environment, and ended when it misbehaves. The core's own code never loads plugin code.
- The honest limit above stands in the ADR, the design documents and the console: do not enable code you would not run on this server.
- The host depends on Node's permission model (Node 26 is the supported runtime). Process flags are checked by the tests, in CI on Linux as well as locally on Windows.
- Not part of this step: container sidecars and the compose fragment, the declarative driver interpreter, brokers for secrets, panel and SSH, plugin settings and storage, UI contributions, CPU limits beyond the deadline, a signal-proof boundary (running plugins under another operating system user, or in a container), recording successful calls (the core features that call a plugin will record what they do).
