# ADR 0027: Enabling plugins, tied to what was approved

Status: accepted

## Context
ADR 0021 let the core find plugins and say whether one is usable. Nothing decided yet which of them may run, who says so, and what that decision is about. The design (`13-plugins-and-opensource.md`, sections 5 and 6) says a plugin is enabled after the administrator approves the permissions it asks for, and that hashes are verified. An approval of "the plugin `dns-example`" is worth little: the code behind that name can be replaced the next minute, and the manifest can be edited to ask for more.

## Decision
- **An approval is of content, not of a name.** The digest of a plugin is a SHA-256 over every file in its directory: the path, the size and the hash of the content of each, in order of path (the `.git` directory of a plugin kept in git is left out). Links anywhere inside a plugin make it invalid: a link could lead a plugin's reads outside its directory. A plugin may weigh at most 2000 files and 32 MiB. The digest is part of what discovery reports; it is cached by what the file system says (names, sizes, modification times) so an unchanged plugin is not read again at every request.
- **What is stored.** The table `plugin_approvals`, one row per plugin id: whether it is enabled, the version, where the directory came from, the digest, the approved permissions (the canonical text of the manifest's `permissions`), when and by whom (the user name at the time, with no foreign key, like the audit log). Rows are never deleted: a disabled plugin keeps the record of what was once approved, so the page can say what changed since.
- **Enabling shows the digest and approves exactly it.** `POST /plugins/{id}/enable` (`plugins:manage`, step-up) carries the digest the administrator was shown. If the files differ by then the answer is 409 and nothing is enabled; so is an attempt to enable a plugin that is invalid or for other versions of Swellwright. There is no way to approve code one has not been shown.
- **A plugin that is not what was approved does not stay enabled.** Whenever the list is read, and when Swellwright starts, every enabled plugin is compared with its approval; one that is gone (`missing`), unusable (`unavailable`) or has other files (`changed`) is switched off in one transaction with a `plugin.disabled` record (no actor, the reason in the details). A plugin that changed while Swellwright was off cannot come back switched on. Enabling it again is a new approval of the new digest; the page shows what its permissions differ by from the approved ones (`permissionDiff`) and whether it asks for more.
- **Disabling** (`POST /plugins/{id}/disable`, `plugins:manage`, step-up) switches off at once, keeps the approval on record, and is recorded once (`plugin.disabled`, reason `administrator`); disabling what is not enabled changes and records nothing.
- **Permissions.** `plugins:read` (every built-in role) lists plugins and what each asks for; `plugins:manage` (the owner) enables and disables, and is a step-up permission, so no API token can hold it (ADR 0017, 0023). The routes declare it and the contract test enforces it. Every enabling is recorded as `plugin.enabled` with the version, trust, digest and the counts of what was approved.
- **Where plugins come from.** `SW_PLUGINS_OFFICIAL_DIR` (trust `official`) and `SW_PLUGINS_LOCAL_DIR` (trust `local`), one sub-directory per plugin. Neither set: no plugins and the page says how to add them. The image sets none: the plugins of the monorepo are skeletons until they have a manifest.
- **The console.** Settings → Plugins lists them with status, trust and kinds; the detail dialog shows what the plugin asks for, the digest, a warning for `local` code and, for a changed plugin, the previous approval and the difference.

## Consequences
- The approval that was given is the approval that holds: replacing a file, adding one, editing the manifest or changing the version makes the plugin `changed` and switches it off until someone looks again.
- **Nothing here runs a plugin.** Enabled means approved; the plugin host that runs enabled plugins in isolation (a worker process, the network through the core, limits) is the next step. Until then enabling has no effect on what the core does, which is why a plugin being switched off by a change is safe to do without further coordination.
- `trust` is still only where the directory came from. The manifest's `signature` is shown as present and **not verified**; the page says it proves nothing. Verification, a registry and an SBOM come later (ADR 0008).
- The cache of digests is keyed by names, sizes and modification times, so a file edited to the same size within the clock's resolution would not be noticed until another change. The check at start and the approval itself read the files when the signature differs; a plugin directory is not a place for an attacker who can already write there (the instance's administrator is trusted with it, ADR 0008).
- Not part of this step: running plugins, plugin settings and storage, the registry and downloads, signature verification, updates with a permission diff before they are applied (the diff is shown after the fact for a changed plugin; nothing is downloaded), removal of a plugin's data.
