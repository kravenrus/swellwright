# ADR 0024: Rotating the keys of the vault

Status: accepted

## Context
ADR 0018 built the vault with three layers of keys: the passphrase (through Argon2id) and a recovery key each wrap the key-encryption key (KEK); the KEK wraps a data key (DEK) per secret version; the DEK encrypts the value. It deliberately left rotation for later. The design (`05-security.md`, section 2) asks for rotation of the KEK (re-wrapping without re-encrypting the data) and of the DEKs, and for the passphrase and the recovery key to be replaceable. A passphrase that may have been seen, a recovery key that was printed and lost, or a policy of rotating every year must not mean "export everything and start again".

## Decision
Four operations, each needing `vault:manage` and a fresh second factor (ADR 0017), and each recorded in the audit chain in the same transaction as the change. None of them puts a key, a passphrase or a value into the log.

- **Change the passphrase** (`POST /vault/passphrase`). Needs the current passphrase and a new one (at least 16 characters, different). The KEK does not change: it is wrapped again under a key derived from the new passphrase with a **new salt and the current cost settings** (so changing the passphrase also raises the Argon2id cost to what the server is configured for now). Nothing else is written: no secret, not the recovery wrap. It works while the vault is sealed, because the current passphrase is the proof. `vault.passphrase.changed`.
- **Issue a new recovery key** (`POST /vault/recovery-key/rotate`). Needs the passphrase. The KEK is wrapped under a new random recovery key, shown once in the answer, and the old recovery key stops working at once. Nothing is re-encrypted. `vault.recovery_key.rotated`.
- **Replace the KEK** (`POST /vault/rotate-kek`). Needs the vault open and the passphrase. A new KEK wraps the data key of every secret (the values are not re-encrypted: they stay under their data keys), the key version moves forward, the passphrase wrap gets a new salt, and **a new recovery key is issued**, because the old one opened the old KEK and the recovery key is never stored, so the new KEK cannot be wrapped under it. All or nothing: one transaction, a data key that does not open under the current key aborts the whole thing with nothing changed and the old key still in memory. `vault.kek.rotated` (new version, number of secrets).
- **Encrypt every secret under a fresh data key** (`POST /vault/rotate-data-keys`). Needs the vault open. Every current value is decrypted in memory and encrypted again under a new data key wrapped by the current KEK; versions and `valueChangedAt` do not change. All or nothing. `vault.data_keys.rotated`.
- **The second proof.** Everything that replaces a key the passphrase or the recovery key protects asks for the **passphrase again** on top of the step-up: a stolen, freshly elevated session still does not have it. Rotating the data keys needs only the step-up (it cannot lock anyone out).
- **Nothing runs between "take the key" and "write the secret".** Everything that reads or replaces the key in memory, or writes a secret under it (setup, unseal, seal, create, replace a value, reveal and the four rotations), goes through one in-process queue, so a rotation cannot run in the middle of another request and leave a value wrapped under a key that is gone. The database transaction adds two checks for the case of a second process: an advisory lock, and the key version and secret version must be unchanged when it writes (otherwise 409 and nothing is written).
- **Wrong passphrases count, successes do not.** A wrong passphrase in a rotation is recorded (`vault.unseal.failed`, with the purpose) and counts, like a wrong unseal, towards one limit for the whole vault: ten failures in fifteen minutes block every further try (429). A change from ADR 0018: it counted every try, so rotating and unsealing a few times in a day could lock the vault; it now counts only failures. The limit is in memory, like the others.
- **The status shows when each part was last rotated** (`passphraseChangedAt`, `recoveryKeyRotatedAt`, `kekRotatedAt`, `dataKeysRotatedAt`; null: never since setup), so the console can say how old a key is.

## Consequences
- A leaked passphrase is answered by changing it (seconds, no re-encryption). A lost recovery key by issuing a new one. A suspected KEK exposure by rotating the KEK, and, if the database itself was copied, by rotating the data keys as well; neither needs the secrets to be re-entered.
- Rotating the KEK invalidates the printed recovery key: the person doing it must store the new one before closing the dialog (the console does not let them close it before they confirm).
- The cost of a rotation is proportional to the number of secrets and runs in one transaction (a minute at most before it is abandoned); a vault with thousands of secrets would want batching, which is not needed at the scale of a fleet's credentials.
- Not part of this step: rotating secrets on a schedule and the wizards for panel tokens, DNS and SSH keys (they need the plugins that own those secrets), Shamir shares of the recovery key, a key file as a second factor, export.
