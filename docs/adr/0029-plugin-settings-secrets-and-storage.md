# ADR 0029: Plugin settings, secrets and storage

Status: accepted

## Context
A plugin that talks to a DNS provider needs an account, a zone and a TTL, and a plugin that keeps a cursor needs somewhere to keep it. ADR 0027 and 0028 let the administrator approve what a plugin asks for (including kinds of secret) and run it; they gave it only `fetch`. The design says the settings schema builds the form, secrets live in the vault and are handed over for the duration of a call and only of the declared kind, and a plugin has an isolated storage with no migrations of its own.

## Decision
- **The settings schema is a small, closed subset of JSON Schema** (`config.schema` in the manifest, parsed by `@swellwright/plugin-api`): an object with at most 32 fields; a field is a string (with length limits and an optional closed list of choices), an integer, a number (with limits), a boolean, or a reference to a secret (`"x-sw-secret": "dns-oauth"`); defaults and a `required` list. Unknown keywords and types are refused, and so is `pattern`: a regular expression from a plugin run against what an administrator types could hang the core. A manifest whose schema is not sound, or that refers to a secret kind it does not ask for in `permissions.secrets`, or to a kind the vault does not have, is **invalid** with the reasons (the kind `dns-oauth` is the vault type `dns_oauth`).
- **Settings are the administrator's, stored apart from the plugin.** `GET /plugins/{id}/config` (`plugins:read`) returns the form and the values; `PUT` (`plugins:manage`, step-up) replaces them after every value is checked against the form (types, limits, choices, required; a field the schema does not name is refused, so a typo is an error). The settings are not part of the digest: changing them does not need a new approval, because they cannot give the plugin more than was approved. Each change is recorded as `plugin.config.updated` with the names of the fields that changed and never their values.
- **A secret is chosen, never typed here, and never stored in the settings.** A secret field holds the id of a vault secret; saving checks that it exists and is of the vault type the field's kind names. The plugin gets it by asking: `context.secret(field)` goes to the core, which checks that the field declares a secret, that the kind is in the **stored approval** (not the manifest as it is now), that a secret is bound, and that the vault is unsealed, then reads and decrypts it (`VaultService.readForPlugin`, serialized with the vault's other operations). It is not a reveal: no person asked, so no `secret.revealed`; the use is recorded as `plugin.secret.used` (the field and the secret's id, never the value), once per ten minutes per secret however often it is asked for. A sealed vault, a deleted secret or one of another type is an error to the plugin.
- **What "for the duration of a call" can and cannot mean.** The core hands a secret over only while the plugin is running a call that asks for it, and never puts it in the settings, the environment or a log. It cannot make the plugin forget it: a plugin that keeps a value in memory keeps it until its process ends (idle processes are stopped, ADR 0028). Treat a plugin you enable as someone you trust with the secrets it asks for.
- **The settings go with every call.** The host fetches the settings (without the secret fields) before each call and passes them as `context.config`. A plugin with required settings that are not filled in is not called, and the error says which (`not_configured`); a check, which only loads it, still works.
- **A storage of its own.** `context.storage` has `get`, `set`, `delete` and `keys`; the data is JSON, in the table `plugin_storage` under the plugin id, which no other plugin's context can name. Limits: keys of 1 to 128 characters, values of at most 64 KiB, at most 1000 keys and 4 MiB in all; writes of one plugin are serialized under an advisory lock so two requests cannot beat the totals; replacing a value is judged by what it adds.
- **One door for everything the core does for a plugin.** The IPC channel carries a single kind of request from the plugin (`core`, with an operation: `fetch`, `secret`, `storage`) and one kind of answer; the host gives the process a `CoreServices` object limited to that plugin and to its approval. The interpreter of declarative drivers (ADR 0030) uses the same services.
- **Console.** Plugins, in a plugin's detail dialog: a form drawn from the declared fields, a secret picker listing the vault's secrets of the right kind (names only), the problems with stored values, and who changed them last.

## Consequences
- A real plugin can now be configured and given credentials without anything secret in the settings table, in the audit chain or on the page.
- A running process keeps the approved secret kinds and network list it was started with; they change only through a new approval, which needs a changed plugin, which is switched off, which ends the process.
- Not part of this step: the layout hints of `ui.settings` (the form is generated), secret fields that hold a structured credential (one secret is one text value), per-field secret rotation hooks, exporting a plugin's storage, removal of a plugin's settings and storage when the plugin is deleted (they stay, like approvals).
