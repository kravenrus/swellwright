# ADR 0013: Prisma for the data layer

Status: accepted

## Context
ADR 0001 aligns the stack with the panel (PostgreSQL with Prisma) and ADR 0012 postponed the Prisma major version to the first model. ADR 0009 forbids dependency lifecycle scripts. Checked on a scratch install of Prisma 7.10.1 (2026-11-18):

- The client has no query-engine binary. Queries are compiled by a WASM module and sent through a driver adapter (`@prisma/adapter-pg` over `pg`).
- Migrations are different. `migrate` runs a native **schema engine** binary (about 20 MB). It is not fetched by an install script but by the CLI itself, on first use of any command (`generate` included), from `binaries.prisma.sh`. `--ignore-scripts` therefore does not prevent the download. `generate` does not execute the binary, `migrate` and `migrate diff` do. Prisma 7 has no configuration option to migrate without it.
- Prisma 8 is a release candidate: the npm tag `latest` points to `8.0.0-rc.34` while the stable line is 7.10.x.

## Decision
- Prisma **7.10.1**, pinned exactly (client, adapter and CLI). Moving to 8 is a deliberate change once it is stable and older than the release-age window of ADR 0009.
- The data layer is `packages/db`, shared by the API and the worker: the schema, the migrations, the generated client and a `Database` class (one Prisma client over one connection pool per process). The generated client is not committed; `prisma generate` is the first step of the package's build and typecheck.
- Migrations are committed SQL under `packages/db/prisma/migrations`, applied with `migrate deploy`. A merged migration is never edited. CI applies them to a clean PostgreSQL and fails when the resulting database differs from the schema (`migrate diff --from-config-datasource --to-schema --exit-code`).
- Naming: tables and columns are snake_case in the database, camelCase in the client. Ids are UUID v7 generated by the client (PostgreSQL 17 has no `uuidv7()`).
- `/ready`: the `postgres` check passes only when the server answers **and** every migration shipped with the build is applied. Otherwise it reports the short code `MIGRATIONS_PENDING`, or `SCHEMA_AHEAD` when the database has migrations the build lacks (an older build against a newer schema).
- **Schema engine supply chain.** Every command that can run the binary goes through `packages/db/scripts/prisma.mjs`. It compares the SHA-256 of the downloaded engine with `engine-checksums.json` (pinned per engine commit and platform) before the binary can run, removes the file on a mismatch, refuses `PRISMA_SCHEMA_ENGINE_BINARY` (it would bypass the check) and requires `SW_DATABASE_URL` (without a datasource Prisma 7 prints nothing and exits 0 for some commands). A platform without a pin fails in CI and needs an explicit opt-in locally. The pins for `debian-openssl-3.0.x` (CI, Docker) and `windows` were taken from the checksums published next to the binaries and confirmed by hashing a separately downloaded copy.
- The first model is `User` (login name, optional e-mail, one of the five built-in roles, status, language, theme). Credentials, sessions, permissions, the audit log and the vault tables follow in their own migrations.

## Consequences
- The data layer matches the panel's stack and is typed end to end. A database that is behind or ahead of the code is visible in `/ready` instead of surfacing as a failing query.
- Upgrading Prisma means pinning the new binaries by hand: a small, deliberate cost that keeps the unscripted-install rule meaningful for the one binary it does not cover.
- The `prisma` CLI is a large development dependency tree (Studio UI, a PGlite development server, database drivers). Because `@prisma/client` lists `prisma` as a peer dependency, pnpm installs the CLI wherever the client is installed. The image build decides whether to keep it or to run migrations in a separate stage. Licenses were reviewed: everything is Apache-2.0, MIT or similar, except `elkjs` (EPL-2.0) inside the CLI's Studio UI, a tool that is neither linked into nor redistributed with the application.
- This corrects ADR 0012, which said Prisma 7 needs no binary: the query engine is gone, the schema engine for migrations is not.
- Considered and not chosen: Kysely with a hand-written migration runner (no binary, but a second data layer to build and a departure from the panel's stack); staying on a Prisma 6 line (older, with a native query-engine library).
