# ADR 0020: The texts of the console, English and Russian, with i18next

Status: accepted

## Context
The design (`07-ui-ux.md`) says the console is English by default and Russian is complete, built on i18next like the panel. Until now every text was written into the components. The first screens already exist, so the cost of converting them is small today and grows with every screen; and a plugin system that adds pages needs a place for the texts of those pages.

## Decision
- **i18next 26 and react-i18next 17**, the same major versions as the Remnawave panel 3.4.x frontend, so panel components can be brought over without a second texts library. The release a project pins must be at least three days old (ADR 0009); the choice was the newest 26.x and 17.x that were.
- **The texts are a package of their own**, `packages/i18n` (`@swellwright/i18n`), plain TypeScript objects, no dependency on i18next. A package can be tested with the same `node --test` as the others; the web console, and later the CLI and plugins, read it. One file per language and namespace: `locales/en/auth.ts`, `locales/ru/auth.ts`. Namespaces are areas of the console (`common`, `nav`, `errors`, `auth`, `users`, `roles`, `audit`, `overview`); a new page adds a namespace.
- **English is the source, and the compiler holds the keys.** `apps/web/src/i18next.d.ts` (not named like `i18n.ts`: TypeScript ignores a declaration file that has a source file of the same name beside it) types `t('key')` and `useTranslation('ns')` against the English catalogue, so a missing or misspelled key is a build error. Texts are not JSON files loaded at run time: they are in the bundle, so the first paint is already in the right language and there is no request that can fail.
- **Another language must match English exactly, and a test says so.** `messages.test.ts` fails the build when a language lacks a key English has or has one it lacks, when a plural form a language needs is missing (the categories come from `Intl.PluralRules`: English `one` and `other`, Russian `one`, `few`, `many`, `other`) or one it does not need is present, when a `{{placeholder}}` differs, when a text is empty, or when a Russian sentence is identical to its English source (an untranslated copy; short technical words may match).
- **Which language.** The person's choice, kept in `localStorage` of the browser (`sw.language`); otherwise the first language of the browser that the console has; otherwise English (`pickLanguage`, tested). The account menu has the switch; `<html lang>` follows it. The choice is not stored on the server yet: that needs a call to change one's own preferences, which is a contract change of its own and comes with the rest of the user settings.
- **Dates and numbers follow the language** through `Intl` (`useDateTime`, `useNumber`), never through a formatter made once at the top of a file, which would not follow a change of language.
- **What is not translated.** Technical data shown as data (audit action ids, permission ids, usernames, identifiers), the product name, and messages that come from the server (they are English; the console has its own text for every error code and shows the server's text only where it names a specific cause, as with a name that is taken). Role names and permission descriptions come from the API in English; the console has translations keyed by their ids and falls back to the server's text for an id it does not know, so a permission added by a newer server still displays.
- **Plural and word order are the catalogue's job.** A sentence is one text with placeholders, never pieces joined in code; counts use `t('key', { count })` with plural keys; markup inside a sentence uses `<Trans>`.

## Consequences
- A component declares the namespaces it uses (`useTranslation(['users', 'common'])`); a key from another namespace is a compile error otherwise. A new screen is written with `useTranslation` from the start; reviewers can reject a hard-coded sentence. The build catches the rest (a missing Russian text is a failed test, not a mixed-language screen found later).
- Adding a language is one directory, one entry in `LANGUAGES` and `LANGUAGE_NAMES`; the test then lists everything it lacks.
- Known limits: two languages; texts ship in the bundle, so the bundle grows with every language (lazy loading per language is possible later without changing the keys); the language is per browser, not per user, until user settings exist; API error messages that carry free text stay English.
