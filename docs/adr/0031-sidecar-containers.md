# ADR 0031: Sidecar containers for plugins by others

Status: accepted

## Context
ADR 0028 measured that a plugin process, whatever the Node permission model takes from it, can still signal another process of the same user, the core included: in-process isolation is not a boundary against hostile code. The design (`13-plugins-and-opensource.md`, section 6) answers that for plugins by others: **container sidecars**, a compose service that talks to the core over an internal network, with no access to the core's database and secrets, a network policy, resource limits, and no `docker.sock` for the core. Adding a plugin generates a compose fragment that the administrator applies.

## Decision
- **A sidecar is the way plugins by others run code.** The manifest names it (`"provides": [{ "kind": "DnsProvider", "sidecar": true }]`) and describes the container (`sidecar`: the image, the port it listens on, memory in MiB, cpus). The image must be **pinned by digest** (`name:tag@sha256:<64 hex>`): a tag can be moved to other content, a digest cannot, so what the administrator approved is what runs. A manifest with a sidecar and one without are both checked as before; entry, driver and sidecar are exclusive for one provided extension.
- **A new trust level, `community`** (`SW_PLUGINS_COMMUNITY_DIR`, after `official` and `local`). A community plugin may not bring code to run in the process of Swellwright (`entry`): it is invalid with that reason. It may be a sidecar or a declarative driver. A `local` plugin, which is the administrator's own responsibility, may still run code in the restricted process.
- **Swellwright never starts a container.** It has no access to the container engine. `GET /plugins/{id}/sidecar` (`plugins:manage`, step-up) returns a Docker Compose fragment: the sidecar on a network that is `internal` (no way out), `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, a user that is not root, memory (with no swap), cpu and process limits, a small `/tmp` in memory, no volumes, no published ports, no host network; and the service of the core joining that network to reach it. The administrator saves it and runs `docker compose ... up -d`. The names of the network and of the core's service are configuration (`SW_PLUGIN_NETWORK`, `SW_PLUGIN_CORE_SERVICE`), as is how the core reaches a sidecar (`SW_PLUGIN_SIDECAR_URL`, default `http://plugin-{id}:{port}`) and how the sidecar reaches the core (`SW_PLUGIN_CORE_URL`, default `http://swellwright:3000`). Handing the fragment out is recorded (`plugin.sidecar.exported`).
- **One token proves each side to the other.** The token of a plugin is an HMAC-SHA256 over the plugin id and the **digest of its files**, with a key derived (HKDF) from `SW_AUTH_KEY`; it is not stored and it is in the fragment, so the fragment is a secret. The core sends it to the sidecar (`Authorization: Bearer`) and the sidecar sends it back to the core's gateway. Because the digest is part of it, a changed plugin has another token: a sidecar built for the files that were approved proves nothing for the files that are there now.
- **The protocol is small and HTTP.** `GET /describe` → `{ modules: [{ kind, methods }] }`; `POST /call` with `{ kind, method, params, config }` → `{ ok: true, value }` or `{ ok: false, message }`. The settings (secret fields left out) go with every call as for any plugin (ADR 0029); the call has the deadline of every call and the answer is bounded (4 MiB). A reference implementation in Node, with its manifest and Dockerfile, is `examples/sidecar-node`, and a test runs it for real.
- **The only way out of the container is the core's gateway** (`POST /api/v1/plugins/{id}/gateway`), with the three things a plugin process may ask for (ADR 0028, 0029): a request to the hosts of the stored approval (the same gateway: https, public addresses, bounded, no redirects), the secret bound to a setting, its storage. The route is open to the network (the container is not signed in), so it trusts only the token: **401 for anything that is not exactly the token of this plugin as it was approved, whose files are unchanged and which is enabled**, saying nothing about why; wrong tokens are counted per address (20 per five minutes, then 429, for the right token too while the window lasts) and noted in the audit chain (`plugin.gateway.denied`, capped). Disabling a plugin or changing its files makes the token stop working at once, without restarting anything.
- **Check and call.** A check asks the container what it offers; a container that is not up, or does not accept the token, is an answer (`failed`, with the reason and a hint). A call that cannot reach the container fails with the reason, counts toward the pause after repeated failures (ADR 0028), and shows in the runtime.
- **JSON bodies up to 3 MiB** are accepted by the API now (it was 100 KiB): a request a plugin may send through the gateway is up to 1 MiB, and JSON can double it. The limit is global; a reverse proxy should still bound bodies.

## Consequences
- The honest limit of ADR 0028 has an answer: a plugin by others runs in a container that cannot signal the core (another PID namespace), reads nothing of the host, has no network but the gateway, and is bounded in memory, cpu and processes. What remains is the container engine's own isolation (a kernel or runtime escape), the administrator's choice of image, and the plugin's use of what it was approved for.
- A sidecar sees the settings of its plugin and, when it asks, the secret bound to a field: the same trust as any plugin that was approved for that kind of secret.
- The token in the fragment is as sensitive as the plugin's access: the fragment is shown only after a step-up, never logged, and changes when the files change.
- Not part of this step: pulling or verifying images (the administrator's engine pulls; verifying a signature, for example with cosign, is the administrator's check and the README says to do it), a signature on the manifest, an updater that shows the permission difference before a new image is applied, health checks and restarts beyond the engine's `restart: unless-stopped`, other transports (gRPC), the compose fragment for Kubernetes, running a sidecar without compose.
